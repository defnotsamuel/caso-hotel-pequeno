Diseño lógico de la base de datos

1. Análisis del requerimiento

Entidades: el hotel necesita saber qué habitaciones tiene (12), quiénes se hospedan y cuándo. De ahí salen tres tablas: habitaciones, huespedes y reservas.

Regla crítica: dos reservas activas de la misma habitación no pueden solaparse. Dos rangos [entrada, salida) se solapan si entrada_A < salida_B y salida_A > entrada_B. Entrar el mismo día en que otro huésped sale es válido.

2. Tablas, tipos y llaves

habitaciones

Campo Tipo Restricción
id_habitacion INT PK, AUTO_INCREMENT
numero TINYINT UNIQUE, NOT NULL, entre 1 y 12
tipo ENUM('sencilla','doble','suite') NOT NULL
capacidad TINYINT NOT NULL, > 0
precio_noche DECIMAL(8,2) NOT NULL, > 0

huespedes

Campo Tipo Restricción
id_huesped INT PK, AUTO_INCREMENT
nombre VARCHAR(100) NOT NULL
documento VARCHAR(20) UNIQUE, NOT NULL
telefono VARCHAR(20) NULL
email VARCHAR(100) NULL

reservas

Campo Tipo Restricción
id_reserva INT PK, AUTO_INCREMENT
id_habitacion INT FK → habitaciones.id_habitacion, NOT NULL
id_huesped INT FK → huespedes.id_huesped, NOT NULL
fecha_entrada DATE NOT NULL
fecha_salida DATE NOT NULL, CHECK (fecha_salida > fecha_entrada)
estado ENUM('activa','cancelada') DEFAULT 'activa'

3. Relaciones

habitaciones 1 ────────< N reservas N >──────── 1 huespedes
  • Una habitación puede tener muchas reservas (en distintas fechas); cada reserva es de una sola habitación.
  • Un huésped puede hacer muchas reservas; cada reserva pertenece a un huésped.
  • reservas resuelve la relación muchos a muchos entre habitaciones y huéspedes y aporta atributos propios (fechas, estado).

Normalización: cumple 3FN; ningún dato del huésped o la habitación se repite en reservas, solo sus llaves.

4. Cómo se evitan los duplicados

  1. Consulta de solapamiento antes de insertar.
  2. Transacción con bloqueo (SELECT … FOR UPDATE) para que dos reservas simultáneas no pasen la verificación a la vez.
  3. Trigger que rechaza el INSERT si hay choque, como última barrera (MySQL no tiene restricciones de exclusión por rango). 
CREATE TABLE habitaciones (
  id_habitacion INT AUTO_INCREMENT PRIMARY KEY,
  numero TINYINT NOT NULL UNIQUE CHECK (numero BETWEEN 1 AND 12),
  tipo ENUM('sencilla','doble','suite') NOT NULL,
  capacidad TINYINT NOT NULL CHECK (capacidad > 0),
  precio_noche DECIMAL(8,2) NOT NULL CHECK (precio_noche > 0)
);
CREATE TABLE huespedes (
  id_huesped INT AUTO_INCREMENT PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  documento VARCHAR(20) NOT NULL UNIQUE,
  telefono VARCHAR(20), email VARCHAR(100)
);
CREATE TABLE reservas (
  id_reserva INT AUTO_INCREMENT PRIMARY KEY,
  id_habitacion INT NOT NULL,
  id_huesped INT NOT NULL,
  fecha_entrada DATE NOT NULL,
  fecha_salida DATE NOT NULL,
  estado ENUM('activa','cancelada') NOT NULL DEFAULT 'activa',
  CHECK (fecha_salida > fecha_entrada),
  FOREIGN KEY (id_habitacion) REFERENCES habitaciones(id_habitacion),
  FOREIGN KEY (id_huesped) REFERENCES huespedes(id_huesped)
);
DELIMITER //
CREATE TRIGGER evitar_duplicadas BEFORE INSERT ON reservas
FOR EACH ROW BEGIN
  IF NEW.estado='activa' AND EXISTS (
    SELECT 1 FROM reservas r
    WHERE r.id_habitacion=NEW.id_habitacion AND r.estado='activa'
      AND r.fecha_entrada < NEW.fecha_salida AND r.fecha_salida > NEW.fecha_entrada)
  THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='Habitación ya reservada en esas fechas';
  END IF;
END//
DELIMITER ;

Consulta de disponibilidad: habitaciones sin reservas activas que se crucen con el rango pedido (NOT EXISTS con la misma condición de solapamiento).
